Architecture Overview & Resource Inventory

The deployed architecture establishes bidirectional, non-transitive private connectivity between two non-overlapping Virtual Private Clouds: VPC A (10.10.0.0/16) and VPC B (10.20.0.0/16) in AWS Region {{AWS_REGION}}.

Key Security Characteristic: Neither ewb-app-a nor ewb-app-b possesses a public IPv4 address or direct internet routing. All remote administration is mediated through ewb-bastion in VPC A's public subnet using OpenSSH ProxyJump.

Route Table Configurations & Subnet Associations

To enable packet flow between instances and across the peering link, three distinct route tables are configured with explicit subnet associations:

Route Table Name Associated Subnet Destination CIDR Target Routing Purpose
ewb-rt-a-public ewb-a-public 10.10.0.0/16 local Local VPC A intra-communication
0.0.0.0/0 {{IGW_A_ID}} Internet gateway route for Bastion
10.20.0.0/16 {{PEERING_ID}} Enables Bastion to reach App-B for SSH
ewb-rt-a-private ewb-a-private 10.10.0.0/16 local Local VPC A intra-communication
10.20.0.0/16 {{PEERING_ID}} Forward path: App-A to VPC B workload
ewb-rt-b-private ewb-b-private 10.20.0.0/16 local Local VPC B intra-communication
10.10.0.0/16 {{PEERING_ID}} Return path: VPC B workload back to VPC A
Longest Prefix Match (LPM): In ewb-rt-a-public, traffic toward 10.20.1.10 evaluates 10.20.0.0/16 (more specific) over the default route 0.0.0.0/0, routing SSH ProxyJump traffic directly through the peering connection instead of blackholing it.

Controlled Failure & Recovery Analysis

To definitively prove that the Security Group firewall is actively filtering traffic (and that ping success was not an artifact of an overly permissive rule), a controlled failure was executed by temporarily dropping the ICMP rule.

Fault Injection Procedure: The inbound ICMP Echo Request rule (Type 8, Code 0 from 10.10.2.10/32) was deleted from Security Group ewb-sg-app-b while keeping the SSH rule intact.

Phase A: Failure Observation (Forward Ping from App-A)

[ec2-user@ip-10-10-2-10 ~]$ ping -c 4 10.20.1.10 PING 10.20.1.10 (10.20.1.10) 56(84) bytes of data. --- 10.20.1.10 ping statistics --- 4 packets transmitted, 0 received, 100% packet loss, time 3088ms
Figure 5: Controlled Fault Injection — Temporary deletion of the ICMP Echo Request inbound rule from ewb-sg-app-b

Technical Analysis: Although the VPC route table still successfully routed packets to pcx and delivered them to VPC B, the AWS hypervisor firewall (Security Group) dropped the incoming ICMP Echo Request at the virtual network interface of ewb-app-b. Note that SSH connectivity from Bastion remained fully operational during this period, proving port-level granularity.

Phase B: Recovery Verification

The exact ICMP rule was re-added to ewb-sg-app-b, instantly restoring connectivity:

[ec2-user@ip-10-10-2-10 ~]$ ping -c 4 10.20.1.10 PING 10.20.1.10 (10.20.1.10) 56(84) bytes of data. 64 bytes from 10.20.1.10: icmp_seq=1 ttl=127 time=0.887 ms 64 bytes from 10.20.1.10: icmp_seq=2 ttl=127 time=0.829 ms --- 10.20.1.10 ping statistics --- 4 packets transmitted, 4 received, 0% packet loss, time 3039ms

Technical Defense & Viva Q&A

Q1: Why is the return route needed?
Answer: Network communication is bidirectional. Even if the requester VPC has a route sending packets across the peering connection, the destination host's VPC router needs an explicit route table entry for the return destination CIDR (10.10.0.0/16 -> pcx). Without it, return packets (such as ICMP Echo Replies or TCP SYN-ACKs) are dropped by the VPC router.

Q2: Why is the App-B SSH source the bastion private IP?
Answer: When using SSH ProxyJump, the SSH client establishes a hopped tunnel. The TCP connection to App-B is initiated by the Bastion's kernel using its private ENI IP (10.10.1.10). From App-B's network standpoint, the incoming TCP connection originates from 10.10.1.10, not the student's laptop.

Q3: Why does Active peering not guarantee a successful ping?
Answer: Peering status indicates only that the tunnel is provisioned. Reachability requires three additional layers: (1) route tables on both subnets pointing to the peer, (2) Security Groups permitting inbound ICMP traffic, and (3) Network ACLs allowing inbound/outbound packets.

Q4: Can VPC B use VPC A's internet gateway over peering?
Answer: No. AWS VPC Peering is non-transitive. Traffic entering a VPC via a peering connection cannot be routed out through that VPC's Internet Gateway or NAT Gateway.

Teardown Evidence & Key Learnings

Following project completion and evidence capture, all cloud resources were terminated in reverse dependency order (EC2 instances terminated → Peering connection deleted → Route tables and subnets disassociated → IGW detached → VPCs deleted).

Figure 7: Final Teardown Evidence — EC2 instances transitioned to Shutting-down / Terminated to prevent ongoing cloud charges
Key Takeaway: Designing multi-VPC networks in AWS requires synchronized alignment of Layer 3 IP routing (Route Tables), Layer 4 firewalls (Security Groups), and connection topologies. VPC Peering provides high-throughput, low-latency private connectivity, but requires strict understanding of non-transitivity and explicit bidirectional route definitions.
